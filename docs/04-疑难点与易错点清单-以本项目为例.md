### 1. 工具调用时"用户看不到 tool response"

#### 问题描述

在 Agent 的 system prompt 中，你经常会看到：

```python
instructions = """
    NOTE: THE USER CAN'T SEE THE TOOL RESPONSE.
    ...
"""
```

**这是什么意思？**

#### 原因解释

当 Agent 调用工具（如 `calculator("2+2")`）时：
1. **工具返回原始结果**：`"4"`（或更复杂的 JSON）
2. **用户看不到这个结果**：Streamlit UI 不会直接显示工具调用的原始输出
3. **Agent 需要解释**：LLM 必须将工具结果转换为用户友好的回答

**类比前端**：
- 工具调用 ≈ API 调用返回原始数据
- Agent 解释 ≈ 前端格式化数据并展示给用户

#### 在本项目中的位置

- **System Prompt**：[`src/agents/research_assistant.py`](src/agents/research_assistant.py) 第 44 行
- **工具定义**：[`src/agents/tools.py`](src/agents/tools.py)
- **UI 显示**：[`src/streamlit_app.py`](src/streamlit_app.py) 第 384-429 行（工具调用显示在 status 容器中）

#### 易错场景

**错误理解**：认为工具结果会直接显示给用户

**正确理解**：
- 工具结果会显示在 UI 的"工具调用状态"中（用于调试）
- 但用户的最终回答应该由 LLM 生成，而不是直接显示工具结果

#### 解决方案

确保 system prompt 包含：
```python
instructions = """
    NOTE: THE USER CAN'T SEE THE TOOL RESPONSE.
    
    When you call a tool:
    1. The tool returns raw data
    2. You must interpret and explain it to the user
    3. Don't just repeat the tool output
"""
```

### 2. Streaming 事件结构差异（`subgraphs=True`）

#### 问题描述

在 `message_generator()` 中，代码需要处理两种不同的事件结构：

```python
if len(stream_event) == 3:
    # subgraphs=True: (node_path, stream_mode, event)
    _, stream_mode, event = stream_event
else:
    # 普通: (stream_mode, event)
    stream_mode, event = stream_event
```

**为什么需要这样？**

#### 原因解释

- **普通模式**：事件是二元组 `(stream_mode, event)`
- **`subgraphs=True` 模式**：事件是三元组 `(node_path, stream_mode, event)`

**`subgraphs=True` 用于多 Agent 协作**（如 supervisor-agent），需要知道事件来自哪个子图。

#### 在本项目中的位置

- **代码位置**：[`src/service/service.py`](src/service/service.py) 第 234-240 行
- **使用场景**：`langgraph-supervisor-agent` 和 `langgraph-supervisor-hierarchy-agent`

#### 易错场景

**错误**：假设事件总是二元组，导致解包错误

```python
# 错误：如果 subgraphs=True，这会失败
stream_mode, event = stream_event  # ValueError: too many values to unpack
```

**正确**：兼容两种结构

```python
# 正确：检查长度
if len(stream_event) == 3:
    _, stream_mode, event = stream_event
else:
    stream_mode, event = stream_event
```

#### 解决方案

始终检查事件长度，或使用 try-except：

```python
try:
    if len(stream_event) == 3:
        _, stream_mode, event = stream_event
    else:
        stream_mode, event = stream_event
except ValueError:
    logger.error(f"Unexpected event structure: {stream_event}")
    continue
```

### 3. Interrupt Resume 机制

#### 问题描述

当 Agent 被中断（`interrupt()`）后，下一次请求会被视为"恢复"而不是新消息。

#### 原因解释

**Interrupt 流程**：
1. Agent 执行到 `interrupt("Please provide your birthdate?")`
2. 服务返回中断消息给用户
3. 用户下次请求时，服务检查是否有未完成的 interrupt
4. 如果有，使用 `Command(resume=user_input.message)` 恢复

#### 在本项目中的位置

- **Interrupt 实现**：[`src/agents/interrupt_agent.py`](src/agents/interrupt_agent.py) 第 138 行
- **Resume 处理**：[`src/service/service.py`](src/service/service.py) 第 154-163 行

```python
# 检查是否有未完成的 interrupt
state = await agent.aget_state(config=config)
interrupted_tasks = [task for task in state.tasks if hasattr(task, "interrupts") and task.interrupts]

if interrupted_tasks:
    # 用户输入是 resume 响应
    input = Command(resume=user_input.message)
else:
    # 正常的新消息
    input = {"messages": [HumanMessage(content=user_input.message)]}
```

#### 易错场景

**错误理解**：认为每次请求都是新消息

**正确理解**：
- 如果 Agent 被中断，下一次请求的 `message` 会被视为对 interrupt 的响应
- 需要使用相同的 `thread_id` 才能恢复

#### 解决方案

- **前端**：确保使用相同的 `thread_id` 发送恢复请求
- **后端**：代码已自动处理，无需额外配置

### 4. `agent_config` 保留字段冲突

#### 问题描述

如果 `agent_config` 包含保留字段（`thread_id`、`user_id`、`model`），会返回 422 错误。

#### 原因解释

这些字段已经在 `configurable` 的顶层设置，不能通过 `agent_config` 覆盖。

#### 在本项目中的位置

- **检查逻辑**：[`src/service/service.py`](src/service/service.py) 第 138-145 行

```python
reserved_keys = {"thread_id", "user_id", "model"}
if overlap := reserved_keys & user_input.agent_config.keys():
    raise HTTPException(
        status_code=422,
        detail=f"agent_config contains reserved keys: {overlap}"
    )
```

#### 易错场景

**错误**：
```json
{
  "message": "Hello",
  "agent_config": {
    "thread_id": "xxx"  // ❌ 错误：保留字段
  }
}
```

**正确**：
```json
{
  "message": "Hello",
  "thread_id": "xxx",  // ✅ 正确：在顶层
  "agent_config": {
    "custom_param": "value"  // ✅ 正确：自定义参数
  }
}
```

#### 解决方案

- 保留字段放在请求体顶层
- `agent_config` 只用于自定义参数

### 5. `stream_tokens=false` 时仍会收到 message 事件

#### 问题描述

即使设置 `stream_tokens=false`，你仍会收到 `"message"` 类型的事件（工具调用、中间响应等）。

#### 原因解释

- `stream_tokens` 只控制 **token 粒度**的流式输出
- `"message"` 事件是 **消息粒度**的，不受 `stream_tokens` 影响

#### 在本项目中的位置

- **代码位置**：[`src/service/service.py`](src/service/service.py) 第 306-321 行

```python
if stream_mode == "messages":
    if not user_input.stream_tokens:
        continue  # 跳过 token，但 message 事件仍会发送
```

#### 易错场景

**错误理解**：认为 `stream_tokens=false` 时不会收到任何流式事件

**正确理解**：
- `stream_tokens=false`：不发送 `"token"` 事件，但仍发送 `"message"` 事件
- 用于减少网络流量，但仍能看到工具调用状态

#### 解决方案

客户端需要处理两种事件类型：
```python
match parsed["type"]:
    case "message":
        # 处理完整消息（工具调用、AI 响应等）
    case "token":
        # 处理 token 流（仅当 stream_tokens=true）
```

### 6. Tracing 配置导致启动失败

#### 问题描述

如果设置了 `LANGCHAIN_TRACING_V2=true` 或 `LANGFUSE_TRACING=true`，但缺少必要的 API Key，服务可能启动失败。

#### 原因解释

- **LangSmith**：需要 `LANGCHAIN_API_KEY`
- **Langfuse**：需要 `LANGFUSE_PUBLIC_KEY` 和 `LANGFUSE_SECRET_KEY`

#### 在本项目中的位置

- **设置定义**：[`src/core/settings.py`](src/core/settings.py) 第 110-120 行
- **使用位置**：[`src/service/service.py`](src/service/service.py) 第 132-136 行

```python
if settings.LANGFUSE_TRACING:
    langfuse_handler = CallbackHandler()
    callbacks.append(langfuse_handler)
```

#### 易错场景

**错误配置**：
```bash
LANGFUSE_TRACING=true
# 但缺少 LANGFUSE_PUBLIC_KEY 或 LANGFUSE_SECRET_KEY
```

**结果**：服务启动时可能报错或无法正常追踪

#### 解决方案

- **选项 1**：不启用 tracing（删除或设置为 `false`）
- **选项 2**：配置完整的 API Key
- **选项 3**：使用环境变量检查，避免启动失败

### 7. RAG：向量库路径和 Embedding Key

#### 问题描述

RAG Agent 无法找到向量库或 embedding 失败。

#### 原因解释

- **向量库路径**：默认是 `./chroma_db`（项目根目录）
- **Embedding Key**：需要 `OPENAI_API_KEY`（用于生成 embedding）

#### 在本项目中的位置

- **向量库路径**：[`src/agents/tools.py`](src/agents/tools.py) 第 60 行
  ```python
  chroma_db = Chroma(persist_directory="./chroma_db", embedding_function=embeddings)
  ```
- **Embedding 初始化**：[`src/agents/tools.py`](src/agents/tools.py) 第 52-57 行

#### 易错场景

**错误 1**：向量库不存在
- **症状**：`database_search` 工具报错
- **解决**：运行 `python scripts/create_chroma_db.py` 创建向量库

**错误 2**：缺少 `OPENAI_API_KEY`
- **症状**：`OpenAIEmbeddings()` 初始化失败
- **解决**：在 `.env` 中配置 `OPENAI_API_KEY`

**错误 3**：路径不匹配
- **症状**：找不到向量库
- **解决**：确保 `persist_directory` 路径正确（相对路径相对于运行脚本的目录）

#### 解决方案

1. **创建向量库**：
   ```bash
   # 1. 准备文档（放在 ./data 目录）
   # 2. 运行脚本
   python scripts/create_chroma_db.py
   ```

2. **检查路径**：
   - 确保 `./chroma_db` 目录存在
   - 如果修改路径，同步更新 `src/agents/tools.py` 和 `scripts/create_chroma_db.py`

3. **检查 API Key**：
   - 确保 `OPENAI_API_KEY` 已配置
   - 确保 Key 有效（有余额）

### 8. RAG：Chunk Size 和 Overlap 配置

#### 问题描述

RAG 检索质量差（找不到相关内容或返回不完整信息）。

#### 原因解释

- **Chunk Size**：文档分块大小（默认 2000 字符）
- **Overlap**：块之间的重叠（默认 500 字符）

**影响**：
- Chunk 太大 → 可能包含无关信息
- Chunk 太小 → 可能丢失上下文
- Overlap 太小 → 可能切断句子

#### 在本项目中的位置

- **创建向量库**：[`scripts/create_chroma_db.py`](scripts/create_chroma_db.py) 第 18-19 行
  ```python
  chunk_size: int = 2000,
  overlap: int = 500,
  ```
- **检索数量**：[`src/agents/tools.py`](src/agents/tools.py) 第 61 行
  ```python
  retriever = chroma_db.as_retriever(search_kwargs={"k": 5})  # 返回 5 个文档
  ```

#### 易错场景

**错误配置**：
- `chunk_size=100`：太小，丢失上下文
- `chunk_size=10000`：太大，包含无关信息
- `overlap=0`：可能切断句子

#### 解决方案

- **根据文档类型调整**：
  - 技术文档：`chunk_size=1500-2000`，`overlap=200-300`
  - 对话记录：`chunk_size=500-1000`，`overlap=100-200`
  - 长文章：`chunk_size=2000-3000`，`overlap=500-800`

- **调整检索数量**：
  - 修改 `search_kwargs={"k": 5}` 中的 `k` 值
  - 更多文档 → 更多上下文，但可能包含噪声

### 9. 模型切换时的兼容性问题

#### 问题描述

切换模型（如从 OpenAI 切换到 Anthropic）后，某些功能不工作。

#### 原因解释

不同模型对以下功能的支持不同：
- **Tool Calling**：所有模型都支持，但格式可能略有差异
- **Streaming**：大部分模型支持，但实现方式不同
- **Structured Output**：部分模型支持（如 OpenAI、Anthropic）

#### 在本项目中的位置

- **模型初始化**：[`src/core/llm.py`](src/core/llm.py)
- **Tool Binding**：所有 Agent 文件中的 `model.bind_tools(tools)`

#### 易错场景

**错误**：假设所有模型行为完全一致

**正确理解**：
- 大部分功能兼容，但细节可能不同
- 某些高级功能（如 structured output）可能不支持

#### 解决方案

- **测试不同模型**：确保你的 Agent 在目标模型上正常工作
- **查看模型文档**：了解特定模型的限制
- **使用默认模型**：项目默认模型通常经过充分测试

### 10. Docker 与本地环境变量不同步

#### 问题描述

Docker 容器内的环境变量与本地 `.env` 文件不一致。

#### 原因解释

Docker Compose 需要显式配置 `env_file` 才能读取 `.env` 文件。

#### 在本项目中的位置

- **Docker Compose**：`compose.yaml`（需要检查 `env_file` 配置）

#### 易错场景

**错误**：在本地 `.env` 中配置了变量，但 Docker 容器内读不到

**原因**：`compose.yaml` 中未配置 `env_file`

#### 解决方案

1. **检查 `compose.yaml`**：
   ```yaml
   services:
     agent_service:
       env_file:
         - .env
   ```

2. **或直接在 `compose.yaml` 中设置**：
   ```yaml
   services:
     agent_service:
       environment:
         - OPENAI_API_KEY=${OPENAI_API_KEY}
   ```

3. **重启容器**：
   ```bash
   docker compose down
   docker compose up
   ```
